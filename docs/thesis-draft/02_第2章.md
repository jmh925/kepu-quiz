# 第2章 概念界定与理论基础

## 2.1 信息系统开发方法与教育理论

### 2.1.1 信息系统开发方法

信息系统的开发方法主要有结构化方法和原型法两类。结构化方法强调自顶向下、逐步求精，先完成需求分析与总体设计，再进入编码与测试，各阶段之间界线清楚，适合需求明确且不易变动的系统。原型法则是先快速做出一个可以运行的简化版本，交给使用者试用，根据反馈修改需求，再逐步完善，适合需求在开始阶段不够清晰、需要在使用中逐步明确的情况。

本课题采用以原型法为主、局部结合结构化方法的开发方式，原因有两点。一方面，面向中小学生的科普练习系统在需求上存在不确定性。家长希望孩子多练，学生自己可能更在意是否有趣，教师在意的则是能否看出学生的问题所在，这三方的关注点并不一致，如果一开始就把需求全部固定下来，很容易做出功能齐全但没人愿意用的系统。因此在开发的早期就先做出可以运行的版本，让学生实际用一遍，再根据暴露出来的问题调整功能。另一方面，系统的数据存储、接口约定和学段约束规则属于相对稳定的部分，这部分仍然按结构化的方式预先设计，避免频繁改动造成数据不一致。

在实际推进中，原型法体现为“做一项功能、写一段验收脚本、跑出问题、回改、复跑”的循环。每完成一个模块就补一段可重复执行的检查脚本，把人工观察变成脚本判定。这种方式的一个直接好处是，问题暴露得早而且具体。例如错题本模块在开发过程中出现过“答错的题没有收录”的现象，从界面看只是错题本为空，容易误判成功能没做，而检查脚本定位到真实原因是页面在登录态尚未建立时就把请求发了出去，返回未登录错误且没有重试，属于调用时机问题而非功能缺失。

### 2.1.2 游戏化学习理论

游戏化学习指把游戏中的机制引入非游戏的学习场景，通过即时反馈、目标阶梯、适度的竞争与奖励来维持学习者的参与度。国外对这类机制的实证研究较为充分，Barz等人对学校场景下数字游戏化学习干预的效果所做的元分析，以及Tokac等人对游戏化学习与学生数学成绩关系的元分析，都发现游戏化学习对学习结果整体上有正向作用。

不过这些研究同时提示，游戏化机制的效果与其设计方式密切相关。如果奖励过于强烈，学习者可能把注意力转移到积分和排名上，反而忽略了学习内容本身；如果反馈只有对错而没有解释，参与度提高也难以转化为理解程度的提高。据此，本课题在设计游戏化机制时确定了两条原则。

第一条原则是反馈要具体。每道题判完之后不仅要给对错，还要给出正确选项、涉及的知识点和一段解释；一局结束之后要给复盘报告，指出正确率、薄弱知识点和需要复习的题目。积分和段位只作为学习结果的呈现方式，不作为唯一的反馈内容。

第二条原则是竞争要克制。系统设置了同伴对战和段位阶梯，用于提供短期刺激和长期目标，但在具体设计上作了限制：倒计时到点不判负、不扣分，只提示学生选择答案；答错不使用红色标记，避免产生挫败感；对战失败时的提示是“这次差一点点，再来一局”，而不是直接判定胜负；全站文案不出现“错误”“失败”“排名”这类词。这些限制的目的是让游戏化机制服务于学习，而不是把练习变成纯粹的比分竞争。

## 2.2 前端与后端开发技术

### 2.2.1 前端开发技术

系统的前端包括小程序端和网页端两部分，两者面向不同场景，但采用相同的接口。

小程序端使用微信小程序原生框架开发，由WXML描述页面结构、WXSS描述样式、JavaScript处理交互逻辑，通过`wx.request`调用后端接口，并将登录令牌保存在本地存储中。原生框架不依赖第三方组件库，构建产物小，启动速度快，适合学生和家长在手机上直接打开使用。

网页端（学生端与管理端）采用原生HTML、CSS和JavaScript实现单页应用，不使用前端框架和打包工具。选择这种做法的原因与使用场景有关：管理端的主要使用者是教师和管理人员，使用频率不高，为它引入一套构建工具会显著增加维护成本；网页端学生端则主要用于本地演示和电脑浏览器访问。单页应用通过监听URL的哈希值变化切换视图，用统一的请求封装处理接口调用与错误提示，整个前端没有编译步骤，修改后刷新页面即可生效，便于在开发过程中反复调整。

两端的界面都采用响应式布局。以学生端为例，在390像素宽的手机视口下，顶部导航会折成两行并允许横向滑动，避免把整个页面撑出横向滚动条；同时对所有可点击元素设置了最小尺寸，保证触摸操作的准确性。

### 2.2.2 后端开发技术

后端承担接口响应、业务运算和数据读写三类工作。本系统选择Python作为开发语言，Web框架选用FastAPI，并运行在Uvicorn提供的ASGI服务器上。这样选择的原因有三点。一是Python语法简洁，处理题目校验、经验值结算这类以数据变换为主的工作时表达直接，开发效率较高，第三方库也覆盖了文档解析、数据校验等本系统需要的功能。二是FastAPI基于类型注解定义请求与响应结构，配合Pydantic可以在接口入口自动完成参数校验与类型转换，既减少了手写校验代码，也避免了参数缺漏或类型不符引起的隐蔽错误。三是它原生支持异步处理，在等待大语言模型返回结果这类耗时操作上不会阻塞其他请求。

Django、Spring Boot这类功能更完整的框架不在选择范围内。它们自带的ORM、后台管理和权限体系在本系统中用不到，本系统的接口数量和业务复杂度也远未达到需要它们的程度，引入之后需要额外理解框架约定，反而不利于把注意力集中在业务逻辑上。这说明后端框架的选型应当与项目规模匹配，功能更全并不等于更合适。

接口设计遵循RESTful风格，统一使用`/api/v1`作为前缀，通过HTTP方法表达操作语义：`GET`用于查询，`POST`用于创建或触发动作，`PUT`用于修改，`DELETE`用于删除。资源用名词的复数形式表示，例如`/wrong/questions`表示错题资源，`/admin/users/{user_id}`表示指定用户。所有接口返回统一的JSON结构，由状态码、提示信息和数据三部分组成，前端只需判断状态码即可决定后续处理，不需要针对每个接口写不同的解析逻辑。

后端内部按职责分为路由层、业务服务层和数据访问层三层。路由层只负责接收请求、校验参数和返回统一格式的响应，不包含业务判断；业务逻辑集中在服务层，按账号、出题、判题结算、报告、题库、段位、对战等职责分模块组织；数据访问层把SQL语句集中管理，上层模块不直接拼接SQL。这样划分的目的是让每一层的变化原因尽量单一，修改出题策略时不需要动数据访问代码，更换存储方式时也只需要改动数据访问层。

学生端与管理端在鉴权上分开处理：学生端使用登录后签发的JWT令牌，管理端使用管理员令牌，两者互不通用，避免出现学生令牌可以访问管理接口的情况。

## 2.3 数据存储与身份认证技术

### 2.3.1 数据存储技术

系统的数据可以分成两类，存储方式也不同。一类是内容数据，主要是题目，以JSON文件的形式随程序一起存放。这类数据的特点是结构固定、变动不频繁、需要按教学进度整体更新，用文件保存便于直接用文本编辑器增补题目，更新题库时也不会影响已有的学习记录。另一类是运行数据，包括用户账号、闯关会话、答题记录、错题、复盘报告和同伴对战记录，存放在关系型数据库中。

运行数据之所以用关系型数据库而不是文件，原因在于这些数据之间存在明确的关联：一个用户对应多次闯关，一次闯关对应一条答题记录，错题要按错误次数排序，薄弱知识点要按题目分组统计。这类按条件筛选和聚合的查询用文件实现需要把全部数据读入内存再自行遍历，数据量增长后既慢又容易出错，而关系型数据库的索引和查询语句正是为此设计的。

在关系型数据库的具体选择上，本系统使用SQLite。SQLite是嵌入式数据库，整个数据库就是一个文件，不需要单独安装数据库服务，也不需要配置账号和端口。选择它的依据是本系统的实际使用规模：使用者以家庭和班级为单位，并发写入的压力很小，数据总量也在单机可承载的范围内。用SQLite可以省去部署数据库服务的步骤，使系统在一台普通个人电脑上就能完整运行，备份和迁移只需拷贝一个文件。它的局限同样明确：不适合高并发写入，也不支持多台机器共享同一份数据，如果将来需要面向多个学校同时提供服务，就应当更换为MySQL或PostgreSQL这类独立部署的数据库。

数据访问层直接使用Python标准库中的`sqlite3`模块，没有引入ORM框架。这样做的好处是SQL语句完全可见，便于在调试时确认实际执行了哪些查询，也便于针对具体查询做优化；代价是需要自己注意连接管理和参数化查询。在实现中，所有涉及用户输入的查询都使用参数化占位符传入参数，不拼接字符串，以避免SQL注入。数据库启用WAL日志模式，使读操作不会阻塞写操作。数据库在首次启动时自动创建，包括表结构建立和管理员账号的初始化，不需要人工执行建表脚本。

### 2.3.2 身份认证技术

身份认证要解决的问题是确认请求来自哪个用户，并保证这个判断在后续请求中持续有效。常见做法有两种。一种是服务端会话，用户登录成功后服务端保存一份会话记录并下发会话标识，后续请求凭标识查会话；这种做法便于在服务端主动使会话失效，但需要服务端保存状态，在多台服务器之间共享会话还需要额外的存储。另一种是令牌，把身份信息编码进令牌本身并加上签名，服务端只验证签名和有效期，不保存状态。

本系统采用令牌方式，使用的是JWT（JSON Web Token）。JWT是一段经过签名的字符串，由头部、载荷和签名三部分组成。服务端在用户登录成功后签发令牌，把用户标识和过期时间写入载荷，并用服务端持有的密钥进行签名；客户端在后续请求的请求头中携带该令牌，服务端验证签名和有效期后即可确认用户身份。选择这种方式的原因与本系统的形态有关：系统同时有小程序端、网页端和管理端三个入口，它们各自独立发起请求，不需要服务端维护会话，令牌方式在多端场景下更简单，也便于在后端做无状态的水平扩展。

本系统使用HS256算法签名，密钥通过配置文件注入，不写死在代码中，避免密钥随代码一起公开。学生端令牌与管理端令牌使用不同的鉴权路径，管理端接口还额外校验管理员令牌，防止学生令牌越权访问管理功能。令牌设置了有效期，过期后需要重新登录。需要说明的是，令牌一旦签发，在有效期内无法主动作废，这是无状态设计的代价，因此本系统把有效期设置得较短，以降低令牌泄露后的风险。

认证的另一个方面是口令本身的存储。口令既不能明文保存，也不宜使用不加盐的单次哈希，因为相同口令会得到相同结果，攻击者可以用预先算好的对照表反查。系统使用PBKDF2-HMAC-SHA256算法对口令做加盐哈希，迭代次数为12万次，每个账号使用独立随机生成的盐值。盐值的作用是让相同口令产生不同结果，使对照表失效；高迭代次数则提高了逐个猜测口令的计算成本。注册和登录时只保存和比对哈希结果，不保存口令本身，即使数据库文件泄露，攻击者也无法直接得到用户的原始口令。

## 2.4 大语言模型与检索增强生成

### 2.4.1 大语言模型接入与输出约束

大语言模型在本系统中承担两项工作：一是根据学生输入的主题生成题目，二是根据一局的答题情况生成复盘报告。

接入方式上，本系统没有自行训练或本地部署模型，而是通过兼容OpenAI接口规范的HTTP接口调用第三方的模型服务。这样选择的原因是本课题的目标在于验证模型能否服务于出题与反馈这两个具体环节，而不是研究模型本身；调用现成服务可以避免训练所需的算力与数据条件，也不需要在系统中维护模型运行环境。模型名称、接口地址和密钥都通过配置文件注入，更换模型时只需修改配置，不需要改动业务代码。每次调用设置了超时时间，超时或返回异常时按调用失败处理，避免请求长时间挂起。

未配置密钥或调用失败时的处理方式是降级。未配置密钥时，出题环节直接跳过模型，全部从内置题库抽题；已配置但调用失败时，同样回落到题库，并在返回结果中把题目来源标记为题库。这样处理之后，模型从系统的必要依赖变成了可选增强，系统的可用性不再取决于外部服务是否稳定。

把模型接入答题系统还有一个具体问题：模型输出的是自然语言文本，而系统需要的是结构固定的题目数据。如果只是把模型返回的文本直接当作题目展示，就会出现选项数量不对、答案下标越界、字段缺失等情况，这些问题在界面上不一定立刻暴露，却会直接影响判题结果。本课题的处理办法是在三个环节上做约束。

调用环节，在提示词中明确要求返回JSON格式，并给出字段说明和取值范围，例如选项必须是四个、答案必须是对应选项的下标。接收环节，对返回内容先做JSON提取，再做逐题校验，检查题干的长度是否超过当前学段的上限、选项是否有重复、答案下标是否在有效范围内、内容是否命中敏感词，任何一项不合格就丢弃该题。补足环节，如果过滤后剩下的题目数量不够，就从内置题库中按主题抽取题目补齐，抽取时排除题干已经出现的题目，保证下发给学生的题目数量既符合学段要求，又不出现重复。

这套约束的作用不只是提高出题质量，更重要的是把模型的不可靠性限制在一个可处理的范围内：模型可以失败，但系统不能因为模型失败而不可用。

### 2.4.2 关键词检索增强出题

检索增强生成的基本思路，是先从外部资料中检索出与问题相关的内容，再让模型依据这些内容生成答案，从而减少模型凭空编造的情况。本系统在知识库模块中使用了这一思路，但检索方式作了简化。

学生上传讲义后，系统把文本按段落切分成若干片段存入数据库。出题时，系统根据学生选定的资料和主题，在这些片段中检索与主题相关的内容，再把检索到的片段作为依据交给模型出题。题目因此被限定在讲义覆盖的范围内，不会出现讲义里没有的知识点。

需要说明的是，本系统没有采用向量空间模型或向量数据库的做法。向量检索需要把文本转成向量并计算相似度，虽然能捕捉语义上的相近，但会引入额外的模型调用和向量存储依赖，在离线环境下无法工作。本系统采用的是基于关键词匹配的轻量检索：对中文文本先做分词处理，统计主题词在各片段中的出现位置与次数，再结合片段长度做加权排序，取排名靠前的片段作为依据。这种做法的检索精度不如向量检索，但对于讲义这类篇幅有限、术语集中的文本已经够用，而且不依赖任何外部服务，在没有网络的情况下也能完成检索。

这一取舍反映了本课题在技术选型上的一贯考虑：优先保证系统在受限环境下仍然可用，在此基础上再考虑效果优化。
