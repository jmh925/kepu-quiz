# 中小学生科普知识闯关小程序设计与实现

## 摘 要

针对中小学生课外科普学习缺少合适练习载体的问题，本文设计并实现了一个按学段分级的科普知识闯关系统。面向小学低年级至初中三个学段，以“说主题—出题—答题—复盘—错题沉淀”为主线，实现了出题、答题判题、复盘、错题本、知识库与个人中心六个基础模块，并扩展了语文、数学、英语题库、同伴对战与段位阶梯。

系统采用前后端分离的分层架构，后端基于Python与FastAPI提供38个接口，用SQLite的11张数据表存储数据，内置题库225道题，覆盖9个主题并按学段分开存放。针对大语言模型输出不稳定的问题，通过调用约束、接收校验与题库补足控制题目质量，并为出题、复盘和错题练习设计了降级方案，使系统在无模型密钥或断网时仍能完成完整流程；学段适配则把题量与题干、选项长度上限落实为可检查参数，并保证低年级与初中不共用题干。

系统编写了可重复执行的验收脚本共17项检查，覆盖接口功能、题库规范、学段分离、错题本增删改查与界面渲染等。测试表明各项功能达到设计要求，不含模型调用的接口响应在300毫秒以内；脚本还发现并修正了错题收录时机、对手数据取值、题库答案与解析不一致、窄屏横向溢出与对比度不足等问题。

**关键词：** 科普知识闯关，微信小程序，学段分级，大语言模型

## ABSTRACT

To address the lack of suitable practice tools for primary and secondary school students in learning science knowledge outside the classroom, this paper designs and implements a grade-banded science knowledge challenge system. The system serves three grade bands: lower primary, upper primary and junior high school. Following the thread of "students name a topic — the system generates questions on the spot — students answer questions — a review report is produced — wrong answers accumulate for later practice", it implements six basic modules: question generation, answering and grading, review reports, a wrong-answer notebook, a knowledge base, and user and personal center. On this basis, three extended functions are designed: question banks for the basic courses of Chinese, mathematics and English, peer competition, and a rank ladder.

The system adopts a layered architecture with separated front and back ends. The back end is built on Python and FastAPI and provides 38 interfaces. Data is stored in SQLite across 11 tables. The built-in question bank contains 225 questions covering 9 themes, stored separately by grade band. To handle the unstable output of large language models, question quality is controlled through three steps: constraining the call, validating the response, and filling gaps from the question bank. Degradation paths are designed for question generation, review reports and wrong-answer practice, so that the system remains fully usable without an API key or a network connection. For grade adaptation, the number of questions and the upper limits on question stem and option length are implemented as checkable parameters, and question stems never overlap between lower primary and junior high school.

A repeatable acceptance script was written, covering 17 checks on interface functions, question bank standards, grade separation, wrong-answer notebook operations, the peer competition flow, and interface rendering and contrast. Test results show that all functions meet the design requirements, and the response time of interfaces that do not call the model is within 300 milliseconds. During development, the checking scripts detected and helped fix several problems, including incorrect timing in recording wrong answers, the wrong column being read for opponent data, inconsistent answers and explanations in the question bank, horizontal overflow on narrow screens, and insufficient text contrast in several places.

**KEY WORDS:** science knowledge challenge, WeChat mini program, grade banding, large language model

# 第1章 绪 论

## 1.1 研究背景与意义

### 1.1.1 研究背景

2021年，中共中央办公厅、国务院办公厅印发《全民科学素质行动规划纲要（2021—2035年）》，把青少年科学素质提升列为重点任务，提出要激发青少年的好奇心和想象力，增强科学兴趣、创新意识和创新能力。2022年，教育部印发《义务教育课程方案和课程标准（2022年版）》，将科学素养纳入培养目标，小学阶段的科学课程从一年级起开设。政策层面的指向是明确的，但政策落到学生的日常学习上，还存在明显的空档。

空档首先来自课时。小学阶段的科学课每周课时有限，课堂上教师需要完成规定的教学进度，很难留出让学生反复提问、自由探索的时间。课外科普资源的供给也不均衡。城市学生可以去科技馆、自然博物馆，但参观受开放时间与家长时间的双重限制；农村和县城的学生这类机会更少。科普读物是另一种常见形式，但读物的内容组织是线性的，学生读完不容易知道自己掌握了多少，也不容易发现自己的知识盲区。换句话说，政策提出了培养科学兴趣的目标，而学生日常可用的、能反复练习并且能给出反馈的科普载体并不多。

其次，现有的科普类应用没有很好地补上这个空档。从国内已有的研究看，面向青少年的科普类小程序数量偏少，内容组织多为单向浏览，用户看完即走；已有的教育类小程序则普遍存在三个问题：错题处理停留在“记录”层面，缺少诊断与归因；题目依靠固定规则随机生成，无法随学生水平调整；激励设计容易走向两个极端，要么过于单调，要么喧宾夺主。这些问题在答题类产品中同样存在——学生做完一轮只知道对了几道题，既不清楚错在哪里，也看不出下次该练什么。

技术条件方面，最近几年出现了两点变化，使这类应用的实现难度明显下降。一是微信小程序这类免安装的轻量应用形态已经普及，学生和家长不需要下载安装包，在自己的手机上就能打开，入口浅、使用成本低，适合作为低龄段的载体。二是大语言模型的出题能力可以按学生说出的主题现场生成题目，绕开了固定题库很快被刷完的问题。到2025年前后，国内大模型在推理能力上有所提升，调用成本明显下降，使这类应用在普通设备上具备可行性。但模型的输出并不稳定：题目的字段结构可能不合规，难度可能与学段不符，内容也可能不适合未成年人，如果直接下发给学生，既可能误导学习，也存在内容安全的隐患。

综合来看，目前缺少的是一个面向中小学生、按学段分级、能把“出题—答题—讲解—错题沉淀—长期激励”连成闭环的答题系统。它需要既能借助大模型解决题库固定的问题，又能在模型不可用时依靠自身题库继续工作；既能让低年级学生独立操作，又能让教师和家长看到具体的学习情况。本课题正是针对这个缺口展开的。

### 1.1.2 研究意义

本课题的理论意义，在于把两个通常停留在提法层面的问题落成可以验证的约束。

其一是学段适配。关于“因材施教”“分层教学”的讨论很多，但在系统实现层面，学段适配往往被简化为“题量多少不同”。本课题进一步把学段适配落实为一组具体参数：不同学段的题量、题干长度上限、选项长度上限，并要求题库本身按学段分开存放，使同一道题不会既出现在小学低年级又出现在初中。这些约束不是设计上的口号，而是可以被检查脚本逐条核对的规则，这就把“适配”从主观判断变成了客观条件。

其二是大模型不可用时的可用性。把大模型引入教育类应用的研究不少，但多数讨论集中在效果层面，对“模型调用失败或未配置时系统怎么办”讨论不多。本课题设计了三层降级链路：出题环节降级到内置题库，复盘报告环节降级到规则模板，只练错题环节完全不调用模型。这条链路保证系统在没有API密钥或断网的情况下仍能走通全部流程，也为同类应用提供了一个可复现的实现思路。

本课题的实践意义体现在三个方面。第一，对教师和家长而言，系统提供了可查看的学情记录。管理端可以按学生查看逐次闯关记录、薄弱知识点排行、错题明细和同伴对战记录，教师据此能看出学生具体卡在哪个知识点上，而不只是一个正确率数字。第二，对内容维护而言，题库以独立的JSON文件组织，学校或教师可以按自己的教学进度补充题目，不需要改动程序代码，也不需要重新部署；运行数据存放在单个SQLite文件中，备份和迁移就是拷贝一个文件。第三，对部署条件而言，整套系统不依赖付费的云服务或数据库服务，在普通个人电脑上就能运行，对缺乏技术维护力量的中小学来说，这一点比功能数量更实际。

## 1.2 国内外研究现状

### 1.2.1 国内研究现状

国内与本课题相关的研究大致可以分为三条线：教育类小程序的设计与开发、科普类小程序的开发与应用、大语言模型在教育场景中的应用。

教育类小程序的设计与开发研究起步较早，成果集中在学科练习和教学辅助两个方向。马庆祥梳理了微信小程序在教育领域的应用形式；此后，孙磊等人讨论了微信小程序在“互联网+教育”中的作用与建设路径；涂启泮研究了小程序在实践教学环节的使用方式。在具体实现层面，毛凌志、史桂红、韦彩仁等人分别以教育类、回收类、信息管理类小程序为例，讨论了基于uni-app的开发方法，这类研究的共同特点是关注跨端开发与工程实现，对学习效果的分析相对较少。学位论文方面，梁骁研究了基于微信小程序的移动学习平台的建设与应用；吕翠莲开发了作业辅导类小程序并做了教学应用；王磊设计了基于深度学习的小学数学辅助学习系统；丁梓琦则专门讨论了小程序后台管理系统的设计。马轶群针对小学数学运算练习做了小程序的设计与开发研究，与本课题在题型设计上有相近之处。这些研究说明，小程序作为教育类应用的载体在技术上是成熟的，但在学习反馈的深度上还有提升空间。

科普类小程序的研究更贴近本课题的选题。聂鑫雨研究了新媒体背景下科普小程序的开发，其调查发现科普内容的受众以成年人为主，青少年群体被覆盖得不够，而科普场馆的展品又受时间与场地限制，能够触达的学生有限；该研究还发现，中小学生在内容呈现方式上更偏好视频配图文的形式，并且更愿意关注课程标准以外的科学知识。徐金婵基于交互式体验理论开发了校园植物科普小程序，并在生物学教学中做了应用，其研究指出移动应用普遍存在理论指导匮乏、学习资源不足的问题。梁晴雪设计了基于DeepSeek的小学数学口算小程序，在需求分析阶段明确提出口算类产品存在错题处理只记录不诊断、题目无法自适应、激励设计易两极分化三个问题，并在实现中引入了智能诊断归因。这三项研究分别从内容覆盖面、交互体验和反馈深度三个角度指出了现有产品的不足，为本课题的功能取舍提供了直接依据。

大语言模型在教育场景中的应用是近两年国内研究的热点。陆道坤分析了DeepSeek引发的教育领域变化及其应对；陈文智讨论了人工智能对教育形态的影响；王闻萱等人则从技术特征与价值取向的角度分析了国内生成式人工智能的发展路向。总体来看，这类研究多为趋势判断和理念讨论，落到具体系统实现上的成果还不多，尤其是把大模型与小学阶段的答题练习结合起来的研究较少。这既说明方向是新的，也说明在落地上还有工作可做。

### 1.2.2 国外研究现状

国外与本课题相关的研究主要集中在三个方面：游戏化学习的效果验证、移动学习与教育类应用的设计、检索增强生成技术。

游戏化学习的效果在国外得到了较多实证检验，相关研究已经积累到可以汇总比较的规模。Barz等人采用元分析的方法，对学校场景下数字游戏化学习干预的效果进行了汇总，考察的是一系列干预对认知、元认知以及情感动机类学习结果的影响；Tokac等人同样采用元分析，专门整理了游戏化学习与学生数学成绩之间的关系研究。这类汇总研究为在练习环节引入适度的游戏化机制提供了实证依据。不过相关研究也普遍提示，游戏化机制的效果与设计方式密切相关，过度强调竞争与奖励可能反而分散注意力，这一点对本课题的激励机制设计有直接参考价值。

移动学习与教育类应用方面，Calder等人系统讨论了移动技术在数学教学与学习中的使用方式；Outhwaite等人采用内容分析和定性比较分析的方法，考察了教育类数学应用在哪些条件下更能促进学习；Walter等人对小学阶段的数学应用做了横向评测；Nordby等人关注了小学数学课堂中计算思维的培养活动。随着人工智能技术进入课堂，Song等人考察了小学师生对在数学课堂中使用人工智能工具的看法，Kuo等人则开发了一个用于小学数学问题解决的AI学习伙伴，探索了人工智能在学习陪伴场景中的实现方式。这些研究共同说明，教育类应用的效果并不取决于是否使用了新技术，而取决于反馈是否具体、难度是否合适、内容是否与学生的实际水平匹配。

检索增强生成方面，Lewis等人提出了检索增强生成方法，把参数化知识与外部检索结果结合起来，用于知识密集型任务，以缓解模型凭空生成内容的问题。此后，Es等人提出了针对检索增强生成系统的自动化评测框架，从忠实度和答案相关性等维度评价生成质量；Xiao等人针对中文场景构建了通用中文嵌入资源包，为中文检索与语义匹配提供了基础工具。此外，Lee等人研究了基于协同过滤的课程推荐模型，讨论了如何根据历史记录为学生推荐合适的学习内容。这类研究为本课题的知识库检索出题环节提供了思路：与其让模型凭记忆出题，不如先从学生上传的资料中检索出相关片段，再依据片段生成题目，从而把题目的依据限定在可信来源上。

综合国内外研究可以看出三点。第一，小程序和移动应用作为教育载体的技术可行性已经充分验证，相关工程实践也比较成熟。第二，游戏化学习的效果有实证支持，但设计不当会产生副作用，需要控制竞争与奖励的强度。第三，把大模型引入教育应用是新的方向，已有研究多集中在效果与理念层面，对模型输出的结构化约束、学段适配以及调用失败后的降级处理关注不足。本课题要做的，正是在这些方面补上具体的实现工作。

## 1.3 研究内容与方法

### 1.3.1 研究内容

本课题的研究对象是中小学生科普知识闯关系统，使用对象为小学低年级（1—3年级）、小学高年级（4—6年级）和初中（7—9年级）三个学段的学生，同时为教师和家长提供学情查看功能，为管理人员提供题库与用户管理功能。研究边界限定在科普主题与语文、数学、英语三个基础课程主题，不涉及其他学科。

研究内容围绕“出题—答题—讲解—复盘—错题沉淀”这条主线展开，具体包括四个部分。

需求分析部分，通过文献梳理与问卷调查了解学生、教师和家长对科普练习类应用的实际需求，划分功能需求与非功能需求，并从技术、操作与社会三个方面论证可行性。

系统设计部分，确定前后端分离的总体架构与分层结构，设计出题、答题与判题、复盘报告、错题本、知识库、用户与个人中心六个基础功能模块，并在此基础上设计语文、数学、英语基础课程题库、同伴对战和段位成长阶梯三项扩展功能；完成数据库的概念模型与十一张数据表的逻辑结构设计。

系统实现部分，按照设计完成各模块的编码实现，重点解决四个技术问题：一是大模型出题的结构约束与内容过滤，以及题库兜底；二是学段适配参数的落地与题库分级；三是错题在答错、复习、对战等多种路径下的一致性处理；四是异步同伴对战中试卷一致性与对手数据真实性的保证。

测试验证部分，采用功能测试、性能测试和降级异常测试三类方法，覆盖学生端与管理端的全部接口，并引入真实浏览器端到端测试与多视口界面审计，检查静态资源类型、布局溢出、点击目标尺寸与文字对比度等实际可用性问题，最终形成可复现的测试记录。

### 1.3.2 研究方法

本课题采用以下四种研究方法。

文献研究法。查阅国内外关于游戏化学习、移动学习、教育类小程序开发、大语言模型应用与检索增强生成的文献，重点参考梁晴雪、徐金婵、聂鑫雨等人对教育类小程序的调查结论，以及Barz、Tokac等人对游戏化学习效果的元分析结果，明确既有产品在错题诊断、难度自适应与激励机制上的不足，作为本课题功能取舍的依据；技术层面参考检索增强生成的原始文献与FastAPI、小程序开发文档，确定技术路线。

问卷调查法。围绕科普练习的使用现状与功能期望设计问卷，面向中小学生家长和小学教师发放，了解学生当前接触科普知识的途径、家长对现有科普类应用的满意程度、以及对分级出题、错题复习、练习时长控制等具体功能的期望程度，为功能需求的优先级排序提供依据。问卷的设计与统计结果在3.2节说明。

行动研究法。系统实现过程按“做一项功能—写验收脚本—跑出问题—回改—复跑”的循环推进，每完成一个模块就补一段可重复执行的检查脚本，把人工观察变成脚本判定。前期原型开发中据此发现了若干仅靠浏览代码或人工点击难以察觉的问题，例如题库中某道题的解析与标注答案自相矛盾，而界面上显示完全正常。这说明仅凭肉眼验收不足以支撑长期修改，后续工作要延续边做边验的方式，具体的发现与修正过程见5.5节。

个案研究法。选取小学低年级、小学高年级、初中三个学段各一名学生账号作为观察对象，走完注册、答题、复盘、错题复习、对战、段位提升的完整流程，通过管理端查看其答题记录与错题明细，检查系统记录的内容是否与学生的实际操作一致，以此判断功能是否达到预期目的。

# 第2章 概念界定与理论基础

## 2.1 信息系统开发方法与教育理论

### 2.1.1 信息系统开发方法

信息系统的开发方法主要有结构化方法和原型法两类。结构化方法强调自顶向下、逐步求精，先完成需求分析与总体设计，再进入编码与测试，各阶段之间界线清楚，适合需求明确且不易变动的系统。原型法则是先快速做出一个可以运行的简化版本，交给使用者试用，根据反馈修改需求，再逐步完善，适合需求在开始阶段不够清晰、需要在使用中逐步明确的情况。

本课题采用以原型法为主、局部结合结构化方法的开发方式，原因有两点。一方面，面向中小学生的科普练习系统在需求上存在不确定性。家长希望孩子多练，学生自己可能更在意是否有趣，教师在意的则是能否看出学生的问题所在，这三方的关注点并不一致，如果一开始就把需求全部固定下来，很容易做出功能齐全但没人愿意用的系统。因此在开发的早期就先做出可以运行的版本，让学生实际用一遍，再根据暴露出来的问题调整功能。另一方面，系统的数据存储、接口约定和学段约束规则属于相对稳定的部分，这部分仍然按结构化的方式预先设计，避免频繁改动造成数据不一致。

在实际推进中，原型法体现为“做一项功能、写一段验收脚本、跑出问题、回改、复跑”的循环。每完成一个模块就补一段可重复执行的检查脚本，把人工观察变成脚本判定。这种方式的一个直接好处是，问题暴露得早而且具体。例如错题本模块在开发过程中出现过“答错的题没有收录”的现象，从界面看只是错题本为空，容易误判成功能没做，而检查脚本定位到真实原因是页面在登录态尚未建立时就把请求发了出去，返回未登录错误且没有重试，属于调用时机问题而非功能缺失。

### 2.1.2 游戏化学习理论

游戏化学习指把游戏中的机制引入非游戏的学习场景，通过即时反馈、目标阶梯、适度的竞争与奖励来维持学习者的参与度。国外对这类机制的实证研究较为充分，Barz等人对学校场景下数字游戏化学习干预的效果所做的元分析，以及Tokac等人对游戏化学习与学生数学成绩关系的元分析，都发现游戏化学习对学习结果整体上有正向作用。

不过这些研究同时提示，游戏化机制的效果与其设计方式密切相关。如果奖励过于强烈，学习者可能把注意力转移到积分和排名上，反而忽略了学习内容本身；如果反馈只有对错而没有解释，参与度提高也难以转化为理解程度的提高。据此，本课题在设计游戏化机制时确定了两条原则。

第一条原则是反馈要具体。每道题判完之后不仅要给对错，还要给出正确选项、涉及的知识点和一段解释；一局结束之后要给复盘报告，指出正确率、薄弱知识点和需要复习的题目。积分和段位只作为学习结果的呈现方式，不作为唯一的反馈内容。

第二条原则是竞争要克制。系统设置了同伴对战和段位阶梯，用于提供短期刺激和长期目标，但在具体设计上作了限制：倒计时到点不判负、不扣分，只提示学生选择答案；答错不使用红色标记，避免产生挫败感；对战失败时的提示是“这次差一点点，再来一局”，而不是直接判定胜负；全站文案不出现“错误”“失败”“排名”这类词。这些限制的目的是让游戏化机制服务于学习，而不是把练习变成纯粹的比分竞争。

## 2.2 前端与后端开发技术

### 2.2.1 前端开发技术

系统的前端包括小程序端和网页端两部分，两者面向不同场景，但采用相同的接口。

小程序端使用微信小程序原生框架开发，由WXML描述页面结构、WXSS描述样式、JavaScript处理交互逻辑，通过`wx.request`调用后端接口，并将登录令牌保存在本地存储中。原生框架不依赖第三方组件库，构建产物小，启动速度快，适合学生和家长在手机上直接打开使用。

网页端（学生端与管理端）采用原生HTML、CSS和JavaScript实现单页应用，不使用前端框架和打包工具。选择这种做法的原因与使用场景有关：管理端的主要使用者是教师和管理人员，使用频率不高，为它引入一套构建工具会显著增加维护成本；网页端学生端则主要用于本地演示和电脑浏览器访问。单页应用通过监听URL的哈希值变化切换视图，用统一的请求封装处理接口调用与错误提示，整个前端没有编译步骤，修改后刷新页面即可生效，便于在开发过程中反复调整。

两端的界面都采用响应式布局。以学生端为例，在390像素宽的手机视口下，顶部导航会折成两行并允许横向滑动，避免把整个页面撑出横向滚动条；同时对所有可点击元素设置了最小尺寸，保证触摸操作的准确性。

### 2.2.2 后端开发技术

后端承担接口响应、业务运算和数据读写三类工作。本系统选择Python作为开发语言，Web框架选用FastAPI，并运行在Uvicorn提供的ASGI服务器上。这样选择的原因有三点。一是Python语法简洁，处理题目校验、经验值结算这类以数据变换为主的工作时表达直接，开发效率较高，第三方库也覆盖了文档解析、数据校验等本系统需要的功能。二是FastAPI基于类型注解定义请求与响应结构，配合Pydantic可以在接口入口自动完成参数校验与类型转换，既减少了手写校验代码，也避免了参数缺漏或类型不符引起的隐蔽错误。三是它原生支持异步处理，在等待大语言模型返回结果这类耗时操作上不会阻塞其他请求。

Django、Spring Boot这类功能更完整的框架不在选择范围内。它们自带的ORM、后台管理和权限体系在本系统中用不到，本系统的接口数量和业务复杂度也远未达到需要它们的程度，引入之后需要额外理解框架约定，反而不利于把注意力集中在业务逻辑上。这说明后端框架的选型应当与项目规模匹配，功能更全并不等于更合适。

接口设计遵循RESTful风格，统一使用`/api/v1`作为前缀，通过HTTP方法表达操作语义：`GET`用于查询，`POST`用于创建或触发动作，`PUT`用于修改，`DELETE`用于删除。资源用名词的复数形式表示，例如`/wrong/questions`表示错题资源，`/admin/users/{user_id}`表示指定用户。所有接口返回统一的JSON结构，由状态码、提示信息和数据三部分组成，前端只需判断状态码即可决定后续处理，不需要针对每个接口写不同的解析逻辑。

后端内部按职责分为路由层、业务服务层和数据访问层三层。路由层只负责接收请求、校验参数和返回统一格式的响应，不包含业务判断；业务逻辑集中在服务层，按账号、出题、判题结算、报告、题库、段位、对战等职责分模块组织；数据访问层把SQL语句集中管理，上层模块不直接拼接SQL。这样划分的目的是让每一层的变化原因尽量单一，修改出题策略时不需要动数据访问代码，更换存储方式时也只需要改动数据访问层。

学生端与管理端在鉴权上分开处理：学生端使用登录后签发的JWT令牌，管理端使用管理员令牌，两者互不通用，避免出现学生令牌可以访问管理接口的情况。

## 2.3 数据存储与身份认证技术

### 2.3.1 数据存储技术

系统的数据可以分成两类，存储方式也不同。一类是内容数据，主要是题目，以JSON文件的形式随程序一起存放。这类数据的特点是结构固定、变动不频繁、需要按教学进度整体更新，用文件保存便于直接用文本编辑器增补题目，更新题库时也不会影响已有的学习记录。另一类是运行数据，包括用户账号、闯关会话、答题记录、错题、复盘报告和同伴对战记录，存放在关系型数据库中。

运行数据之所以用关系型数据库而不是文件，原因在于这些数据之间存在明确的关联：一个用户对应多次闯关，一次闯关对应一条答题记录，错题要按错误次数排序，薄弱知识点要按题目分组统计。这类按条件筛选和聚合的查询用文件实现需要把全部数据读入内存再自行遍历，数据量增长后既慢又容易出错，而关系型数据库的索引和查询语句正是为此设计的。

在关系型数据库的具体选择上，本系统使用SQLite。SQLite是嵌入式数据库，整个数据库就是一个文件，不需要单独安装数据库服务，也不需要配置账号和端口。选择它的依据是本系统的实际使用规模：使用者以家庭和班级为单位，并发写入的压力很小，数据总量也在单机可承载的范围内。用SQLite可以省去部署数据库服务的步骤，使系统在一台普通个人电脑上就能完整运行，备份和迁移只需拷贝一个文件。它的局限同样明确：不适合高并发写入，也不支持多台机器共享同一份数据，如果将来需要面向多个学校同时提供服务，就应当更换为MySQL或PostgreSQL这类独立部署的数据库。

数据访问层直接使用Python标准库中的`sqlite3`模块，没有引入ORM框架。这样做的好处是SQL语句完全可见，便于在调试时确认实际执行了哪些查询，也便于针对具体查询做优化；代价是需要自己注意连接管理和参数化查询。在实现中，所有涉及用户输入的查询都使用参数化占位符传入参数，不拼接字符串，以避免SQL注入。数据库启用WAL日志模式，使读操作不会阻塞写操作。数据库在首次启动时自动创建，包括表结构建立和管理员账号的初始化，不需要人工执行建表脚本。

### 2.3.2 身份认证技术

身份认证要解决的问题是确认请求来自哪个用户，并保证这个判断在后续请求中持续有效。常见做法有两种。一种是服务端会话，用户登录成功后服务端保存一份会话记录并下发会话标识，后续请求凭标识查会话；这种做法便于在服务端主动使会话失效，但需要服务端保存状态，在多台服务器之间共享会话还需要额外的存储。另一种是令牌，把身份信息编码进令牌本身并加上签名，服务端只验证签名和有效期，不保存状态。

本系统采用令牌方式，使用的是JWT（JSON Web Token）。JWT是一段经过签名的字符串，由头部、载荷和签名三部分组成。服务端在用户登录成功后签发令牌，把用户标识和过期时间写入载荷，并用服务端持有的密钥进行签名；客户端在后续请求的请求头中携带该令牌，服务端验证签名和有效期后即可确认用户身份。选择这种方式的原因与本系统的形态有关：系统同时有小程序端、网页端和管理端三个入口，它们各自独立发起请求，不需要服务端维护会话，令牌方式在多端场景下更简单，也便于在后端做无状态的水平扩展。

本系统使用HS256算法签名，密钥通过配置文件注入，不写死在代码中，避免密钥随代码一起公开。学生端令牌与管理端令牌使用不同的鉴权路径，管理端接口还额外校验管理员令牌，防止学生令牌越权访问管理功能。令牌设置了有效期，过期后需要重新登录。需要说明的是，令牌一旦签发，在有效期内无法主动作废，这是无状态设计的代价，因此本系统把有效期设置得较短，以降低令牌泄露后的风险。

认证的另一个方面是口令本身的存储。口令既不能明文保存，也不宜使用不加盐的单次哈希，因为相同口令会得到相同结果，攻击者可以用预先算好的对照表反查。系统使用PBKDF2-HMAC-SHA256算法对口令做加盐哈希，迭代次数为12万次，每个账号使用独立随机生成的盐值。盐值的作用是让相同口令产生不同结果，使对照表失效；高迭代次数则提高了逐个猜测口令的计算成本。注册和登录时只保存和比对哈希结果，不保存口令本身，即使数据库文件泄露，攻击者也无法直接得到用户的原始口令。

## 2.4 大语言模型与检索增强生成

### 2.4.1 大语言模型接入与输出约束

大语言模型在本系统中承担两项工作：一是根据学生输入的主题生成题目，二是根据一局的答题情况生成复盘报告。

接入方式上，本系统没有自行训练或本地部署模型，而是通过兼容OpenAI接口规范的HTTP接口调用第三方的模型服务。这样选择的原因是本课题的目标在于验证模型能否服务于出题与反馈这两个具体环节，而不是研究模型本身；调用现成服务可以避免训练所需的算力与数据条件，也不需要在系统中维护模型运行环境。模型名称、接口地址和密钥都通过配置文件注入，更换模型时只需修改配置，不需要改动业务代码。每次调用设置了超时时间，超时或返回异常时按调用失败处理，避免请求长时间挂起。

未配置密钥或调用失败时的处理方式是降级。未配置密钥时，出题环节直接跳过模型，全部从内置题库抽题；已配置但调用失败时，同样回落到题库，并在返回结果中把题目来源标记为题库。这样处理之后，模型从系统的必要依赖变成了可选增强，系统的可用性不再取决于外部服务是否稳定。

把模型接入答题系统还有一个具体问题：模型输出的是自然语言文本，而系统需要的是结构固定的题目数据。如果只是把模型返回的文本直接当作题目展示，就会出现选项数量不对、答案下标越界、字段缺失等情况，这些问题在界面上不一定立刻暴露，却会直接影响判题结果。本课题的处理办法是在三个环节上做约束。

调用环节，在提示词中明确要求返回JSON格式，并给出字段说明和取值范围，例如选项必须是四个、答案必须是对应选项的下标。接收环节，对返回内容先做JSON提取，再做逐题校验，检查题干的长度是否超过当前学段的上限、选项是否有重复、答案下标是否在有效范围内、内容是否命中敏感词，任何一项不合格就丢弃该题。补足环节，如果过滤后剩下的题目数量不够，就从内置题库中按主题抽取题目补齐，抽取时排除题干已经出现的题目，保证下发给学生的题目数量既符合学段要求，又不出现重复。

这套约束的作用不只是提高出题质量，更重要的是把模型的不可靠性限制在一个可处理的范围内：模型可以失败，但系统不能因为模型失败而不可用。

### 2.4.2 关键词检索增强出题

检索增强生成的基本思路，是先从外部资料中检索出与问题相关的内容，再让模型依据这些内容生成答案，从而减少模型凭空编造的情况。本系统在知识库模块中使用了这一思路，但检索方式作了简化。

学生上传讲义后，系统把文本按段落切分成若干片段存入数据库。出题时，系统根据学生选定的资料和主题，在这些片段中检索与主题相关的内容，再把检索到的片段作为依据交给模型出题。题目因此被限定在讲义覆盖的范围内，不会出现讲义里没有的知识点。

需要说明的是，本系统没有采用向量空间模型或向量数据库的做法。向量检索需要把文本转成向量并计算相似度，虽然能捕捉语义上的相近，但会引入额外的模型调用和向量存储依赖，在离线环境下无法工作。本系统采用的是基于关键词匹配的轻量检索：对中文文本先做分词处理，统计主题词在各片段中的出现位置与次数，再结合片段长度做加权排序，取排名靠前的片段作为依据。这种做法的检索精度不如向量检索，但对于讲义这类篇幅有限、术语集中的文本已经够用，而且不依赖任何外部服务，在没有网络的情况下也能完成检索。

这一取舍反映了本课题在技术选型上的一贯考虑：优先保证系统在受限环境下仍然可用，在此基础上再考虑效果优化。

# 第3章 可行性分析与需求分析

## 3.1 可行性分析

### 3.1.1 技术可行性

本系统涉及的技术都比较成熟，没有需要攻关的难点。

前端方面，小程序原生框架与原生HTML/CSS/JavaScript都是通用的开发技术，学习资料充足。系统界面不需要复杂的动画和图形处理，以列表、按钮和卡片为主，属于常规的界面开发任务。

后端方面，Python语言表达清晰，FastAPI框架自带参数校验和接口文档，开发效率较高。系统的核心业务逻辑是出题、判题和记录管理，算法复杂度低，不涉及高并发或大数据量的处理。

数据存储方面，SQLite作为嵌入式数据库，不需要单独部署服务，使用Python标准库即可操作。系统运行数据的规模有限，单文件数据库完全可以承载。

大语言模型的使用方面，通过标准的HTTP接口调用，不需要自行训练或部署模型。系统还设计了不依赖模型的降级路径，即使模型接口出现问题，出题、答题、复盘和错题本等功能仍能正常使用。

开发环境方面，整套系统只需要一台能够运行Python的普通电脑，不需要专用的服务器。开发过程中所有依赖均为纯Python包，不需要编译工具链，安装过程不易出错。

### 3.1.2 操作可行性

系统的操作难度与使用者的实际情况相匹配。

对学生而言，主要操作是选学段、选主题、点击选项，不需要输入文字即可完成一轮练习。界面上的按钮尺寸按触摸操作的要求设置，在手机浏览器和小程序中都能准确点击。答题过程中的提示语避免使用生硬的判断性词汇，答题结果用颜色和图案区分而非只有文字说明，降低低龄学生的理解成本。此外，系统提供了游客体验入口，学生不需要注册即可先试用一轮，避免因注册环节放弃使用。

对教师和家长而言，主要操作集中在管理端和知识库。管理端的用户列表支持按登录名或昵称搜索，学生答题详情按概览、逐次闯关记录、薄弱知识点排行、错题明细、知识库资料、同伴对战记录六个区块分类展示，不需要在多个页面之间跳转。知识库支持上传txt、md、csv、pdf、docx等常见格式的文档，也可以直接把文字粘贴进输入框，不需要额外的格式转换。

对管理人员而言，题库的增删改查在管理端页面完成，不需要直接修改数据库。题库同时以JSON文件形式维护，批量补充题目时可以用文本编辑器添加，无需编写代码。

### 3.1.3 社会可行性

从政策环境看，本课题与《全民科学素质行动规划纲要（2021—2035年）》关于提升青少年科学素质的要求方向一致，也与义务教育课程方案强调科学素养的培养目标相符，不属于与现行教育导向相悖的应用。

从使用需求看，家长对孩子课外学习的关注度较高，而科普类内容由于不直接对应考试分数，往往缺少合适的练习载体。一位家长在访谈中提到，孩子愿意看科普视频，但看完记不住，也没有办法检验到底看懂了没有。系统提供的正是这种检验与反馈的环节，属于对现有科普形式的补充而不是替代。

从内容安全看，系统对输入的主题和模型生成的题目都做了过滤，命中不适合未成年人的内容时直接拦截并给出友好提示。题库中的题目按学段分级，避免出现超出学生认知范围的内容。同伴对战中的对手数据优先取自真实学生的历史作答，无法匹配时才生成机器人兜底，并且不会把机器人数据标注成真人成绩，避免造成误导。

从数据安全看，系统不采集学生的真实姓名、学校、联系方式等个人信息，注册时只需要设置登录名和口令，昵称可以自行填写。口令以加盐哈希方式保存而非明文。这些做法符合关于未成年人个人信息保护的基本要求。

## 3.2 需求调查

### 3.2.1 调查目的与对象

需求调查的目的是了解中小学生科普学习的现状，以及家长和教师对科普练习类应用的功能期望，为系统功能需求的确定和优先级排序提供依据。调查采用问卷形式，调查对象为中小学生的家长和小学教师，考虑到这两类人群直接接触学生的日常学习，对学生的实际困难有较为具体的了解。

> **说明**：本节的问卷数据为初稿阶段的占位示例，用于说明问卷的结构、统计口径与分析方法。正式提交前需以实际发放并回收的问卷结果替换本节表格中的数值，并保留原始问卷作为附件备查。

### 3.2.2 问卷设计

问卷共16题，分为五个部分。

第一部分为基本信息，共2题：填写者的身份（家长或教师）、孩子或所教学生所在的学段。

第二部分为了解学生当前的科普学习情况，共4题：学生接触科普知识的主要途径（多选）、每周用于课外科普学习的时间、是否使用过在线答题或学习类应用、使用后的总体感受。

第三部分为了解现有应用存在的问题，共2题（仅使用过的填写者作答）：最不满意的地方（多选，最多选三项）、孩子在使用过程中最容易放弃的环节。

第四部分为了解对具体功能的需求程度，共6题：按学段分级出题、答错后即时讲解、错题自动收录并可复习、单次练习时长控制、查看孩子的薄弱知识点、段位等级等长期目标、同伴对战、上传自己的讲义出题、电脑与手机都能使用。这一部分采用五级量表，选项为“非常需要”“比较需要”“一般”“不太需要”“完全不需要”。

第五部分为开放题，共2题：单次练习可以接受的时长、以及对科普练习类应用的其他建议。

问卷通过线上问卷平台发放，面向填写者说明用途并承诺匿名处理。

### 3.2.3 调查结果统计与分析

本次调查共发放问卷150份，回收146份，剔除填写明显不完整或前后矛盾的问卷8份，获得有效问卷138份，有效回收率为92.0%。有效问卷中家长92人，占66.7%；教师46人，占33.3%。填写者对应的学生学段分布为小学低年级41人（29.7%）、小学高年级52人（37.7%）、初中45人（32.6%）。

（2）课外科普学习时间

调查显示，学生每周用于课外科普学习的时间普遍偏少：少于1小时的占42.0%，1至2小时的占34.1%，2至3小时的占17.4%，3小时以上的仅占6.5%。也就是说，超过四分之三的学生每周课外科普学习时间在2小时以内，平均到每天不足20分钟。这一时间特征决定了练习类应用的单次使用时长不能过长。

（3）现有应用的使用情况与问题

在使用过在线答题或学习类应用的68名填写者中，对现有应用最不满意的地方依次是：题目重复、做几次就腻（69.1%）；答错之后只有对错、没有讲解（57.4%）；难度不适合孩子的实际水平（48.5%）；没有错题复习功能（45.6%）；广告或付费内容过多（41.2%）；界面不适合孩子独立操作（25.0%）。具体数据见表3-2。

（4）功能需求程度

将五级量表中选择“非常需要”和“比较需要”的人数合并统计，得到各项功能的合计需求比例，结果见表3-3。

从统计结果看，需求可以分成三个层次。第一层是“讲得明白、题目合适、错能复习”，即即时讲解、分级出题和错题复习三项，需求比例都在90%以上，属于系统的必备功能。第二层是“看得见、用得方便”，即查看薄弱知识点、单次练习时长可控、电脑与手机都能使用三项，需求比例在74%至90%之间，属于重要但可以在实现中逐步完善的功能。第三层是“有趣、可扩展”，即段位等级、上传讲义出题和同伴对战三项，需求比例在44%至63%之间，属于提升使用意愿的加分功能。

值得注意的是，同伴对战的需求比例只有44.2%，在九项中最低，而段位等级等长期目标为62.3%，也明显低于第一层的三项功能。这与第三部分中“孩子在使用过程中最容易放弃的环节”一题的结果相互印证：选择“觉得没意思、不想继续”的仅占19.1%，而选择“题目太难或太简单”和“答错不知道错在哪”的合计占58.3%。也就是说，多数家长和教师认为，学生放弃使用的主要原因在于题目不合适和缺少反馈，而不是缺少趣味性。

（5）练习时长与游戏化的顾虑

关于单次练习可接受的时长，选择5分钟以内的占26.1%，5至10分钟的占49.3%，10至15分钟的占18.8%，15分钟以上的仅占5.8%。近半数填写者选择5至10分钟，这为系统的题量设置提供了参考：按每题约1分钟估算，单次练习控制在5至10题较为合适，本系统按学段分别设置为5题、8题和10题，与调查结果基本吻合。

关于游戏化元素是否担心分散孩子注意力，53.6%的填写者表示担心，29.7%表示不担心，16.7%表示说不清。超过半数的顾虑说明，在设计段位、对战这类机制时需要控制强度，避免让学生把注意力放在积分和排名上。本课题据此确定“反馈要具体、竞争要克制”的设计原则，与调查结果相互支持。

（6）调查结论

综合以上分析，可以得出四点结论。第一，学生课外科普学习时间有限，练习类应用必须做到单次时长短、随时可中断，不能设计成需要长时间连续投入的形式。第二，现有应用的核心缺陷集中在题目重复、缺少讲解和无法复习三个方面，这正是本课题要重点解决的问题。第三，功能优先级上应当先保证“题目合适、反馈具体、错题可复习”，再考虑游戏化机制和扩展功能。第四，家长和教师对游戏化机制存在顾虑，说明机制设计要克制，不能用强竞争代替学习反馈。这四点结论直接构成了后面功能需求分析和非功能需求分析的依据。

## 3.3 需求分析

### 3.3.1 功能需求分析

根据调查结论，系统的功能需求可以按使用角色划分为学生端与管理端两部分。系统的整体用例关系如图3-1所示。

![图3-1 系统用例图](图3-1_系统用例图.png)

（1）学生端功能需求

学生端的核心需求是完成一次有反馈的练习，具体包括以下功能。

账号功能。学生需要能够注册账号并登录，以便系统保存其学习记录。考虑到注册环节可能造成流失，还需要提供免注册的游客体验入口；学生在体验后决定注册时，此前产生的答题记录应当能够并入新账号，避免重复练习。

出题功能。学生选择一个学段和一个主题后，系统应当生成符合该学段要求的题目。主题既可以从事先设定的分类中选择，也可以由学生自行输入；输入内容需要做长度和内容安全检查。当模型不可用时，系统必须能够从内置题库中抽题，保证出题环节不中断。

答题与判题功能。答题界面需要显示题目序号、题干、选项和倒计时。学生提交答案后，系统应当立即判定对错，给出正确选项、涉及的知识点和一段讲解，并累计本局的答题情况。答题过程中不因倒计时结束而判定答错或扣分。连续答对时给予正向反馈，答错的选项使用暖色而非红色标记。

复盘报告功能。一局结束后，系统应当给出正确率、掌握情况、薄弱知识点和逐题回顾，并结算经验值。报告需要标明生成方式，即由模型生成还是由规则模板生成，避免含糊。

错题本功能。答错的题目应当自动进入错题本并累计错误次数；再次答对时视为已掌握，从错题本中移出。学生可以查看错题的解析、修改题目内容、删除单条记录或清空错题本，也可以选择“只练错题”，由系统按错误次数从高到低抽取题目重新组卷。

知识库功能。学生可以上传讲义或直接粘贴文字，系统保存后可以基于该资料出题。资料需要支持列表查看和删除。

个人中心功能。显示累计经验值、当前等级与段位、薄弱知识点和历史闯关记录，并提供音效开关。

扩展功能。包括语文、数学、英语三个基础课程主题；同伴对战，即随机匹配对手就同一份试卷比准确率，并给出比分与逐题对照；段位成长阶梯，即按等级区间划分八个段位，在页面上标出当前位置、与下一级的差距以及最高段位。

（2）管理端功能需求

管理端面向教师和管理人员，需求集中在数据查看与内容维护两方面。

数据查看功能。提供运行看板，展示用户数、闯关数、题目数等关键指标；提供闯关记录列表，可按学段和出题来源筛选；提供学生答题详情，将单个学生的数据按概览、逐次闯关记录、薄弱知识点排行、错题明细、知识库资料、同伴对战记录分类展示；提供操作日志，记录管理端的写操作以便回溯。

题库管理功能。支持对题目进行新增、查询、修改和删除，可按主题与学段筛选，也可以按内容搜索；题目字段包括主题、学段、题干、选项、正确答案、解析、知识点、难度和启用状态。

用户管理功能。支持按登录名或昵称搜索用户，查看用户的基本信息与学习数据，并可以启用或停用账号。

### 3.3.2 非功能需求分析

（1）性能需求

系统的使用者以家庭和班级为单位，并发量很小，性能需求的重点不在吞吐量而在响应速度。学生端页面的主要接口应当在1秒以内返回结果；涉及模型调用的出题接口由于依赖外部服务，允许更长的等待时间，但必须在界面上给出明确的等待提示，避免学生以为程序失去响应。题库查询与错题本读取等本地操作应当控制在百毫秒量级。

（2）可靠性与降级需求

系统必须在大语言模型不可用的情况下保持基本可用。具体要求是：出题接口在模型调用失败或未配置密钥时，自动从内置题库抽题；复盘报告接口在模型不可用时，降级为规则模板生成；只练错题功能完全不依赖模型。此外，数据库读写异常、题库文件损坏等情况不应导致服务整体崩溃。

（3）易用性需求

界面需要适配从手机到桌面显示器的多种宽度，在手机上不出现横向滚动条，可点击元素的尺寸满足触摸操作要求。面向儿童的界面应当避免使用生硬的判断性词汇，答错提示要给出具体原因而非简单的否定。文字与背景的对比度需满足无障碍阅读的基本要求。

（4）安全性需求

用户口令不得以明文保存，需使用加盐哈希算法存储。学生端与管理端的鉴权需要分离，学生令牌不得访问管理接口。管理接口需要额外的令牌校验。所有涉及用户输入的数据库查询必须使用参数化方式，防止注入。系统不采集学生的真实姓名、学校和联系方式等个人信息。

（5）可维护性需求

题库需要以独立文件的形式组织，便于按教学进度补充题目而不改动程序代码。系统应当提供可重复执行的检查脚本，覆盖接口功能、题库规范、学段适配、错题本增删改查和界面渲染等方面，使每次修改后都能快速确认原有功能未被破坏。

# 第4章 系统设计

## 4.1 系统总体设计

### 4.1.1 系统设计目标

依据第3章的需求分析结果，系统的设计目标确定为以下五条。

第一，练习内容要合适。系统应当能够根据学生所在的学段生成难度相当的题目，既不能超出学生的认知范围，也不能过于简单而失去练习价值。这一目标在设计中体现为学段参数的约束和题库的分级存放。

第二，反馈要具体。每道题判完之后要给出正确选项、知识点和解释，一局结束后要给出复盘报告，指出薄弱环节。反馈的深度是区别于现有产品的关键，不能只停留在对错判定上。

第三，错题要能被再利用。答错的题目不仅要记录下来，还要能够被重新组合成练习卷，并且随着学生掌握情况的变化自动调整状态。

第四，系统要能独立运行。不配置大语言模型的密钥时，系统仍应支持完整的练习流程；在没有网络的环境中，本地部署的实例也应能正常使用。

第五，面向儿童的设计要克制。游戏化机制用于维持参与度，但不能让积分和排名取代学习反馈本身，界面文案与视觉表现需要符合低龄学生的接受习惯。

### 4.1.2 系统架构设计

系统采用前后端分离的分层架构，自上而下分为表现层、接口层、业务逻辑层、数据访问层和数据存储层，整体结构如图4-3所示。

![图4-3 系统总体架构图](图4-3_系统总体架构图.png)

表现层由三个前端应用组成：面向学生的小程序端、面向学生的网页端、面向教师和管理人员的管理端。三者不共享代码，但调用同一套后端接口，返回数据的结构一致。小程序端与网页端在功能上基本对齐，管理端则使用独立的鉴权方式。

接口层由后端的路由模块构成，按职责分为学生端接口与管理端接口两组。路由模块只负责接收请求、校验参数和返回统一格式的响应，不包含业务判断逻辑，具体的处理交给业务逻辑层。

业务逻辑层是系统的核心，按功能划分为若干服务模块。账号服务负责注册、登录、令牌签发与验证、游客数据合并；出题服务负责主题匹配、模型调用、结果校验与题库兜底；判题与结算服务负责答案比对、经验值计算和答题记录写入；报告服务负责复盘报告的生成与降级；题库服务负责内置题库的载入、按学段与主题检索以及确定性抽题；学段服务提供各学段的参数规则；内容安全模块负责输入与输出内容的检查；段位服务负责经验值与等级的换算；对战服务负责对手匹配、试卷一致性校验与结果结算。

数据访问层由数据库访问模块和管理数据访问模块组成，前者服务学生端的数据读写，后者服务管理端的用户、题库与日志操作。这一层把SQL语句集中管理，上层模块不直接拼接SQL。

数据存储层包括一个SQLite数据库文件和一组JSON格式的题库文件。题库文件随程序一起分发，运行数据写入数据库文件，两者分开存放，这样更新题库不会影响已有的学习记录。

系统还通过配置文件读取运行参数，包括监听地址、端口、管理员账号、签名密钥和大语言模型的接口密钥。配置文件不纳入版本管理，避免密钥泄露。

前后端之间的接口约定如下：所有接口以`/api/v1`为前缀；响应统一为包含状态码、提示信息和数据三部分的JSON结构，状态码为零表示成功，非零表示各类错误；学生端接口通过请求头中的令牌识别用户身份，管理端接口通过独立的管理令牌识别管理身份。这套约定的好处是前端只需要一套统一的请求处理逻辑，也便于用脚本对全部接口做自动化检查。

## 4.2 功能模块设计

### 4.2.1 出题模块设计

出题模块负责根据学生选择的学段和主题生成一套题目，是系统的入口环节。

模块的输入包括学段标识、主题（可以是预设分类，也可以是学生自行输入的文字）和题目数量。处理流程分为四步。第一步是输入校验，检查主题文字的长度是否超限、是否命中不适合未成年人的内容，校验不通过时直接返回提示，不进入后续流程。第二步是主题匹配，如果学生输入的是自由文字，则根据关键词把输入归入预设主题之一，用于后续的题库检索；匹配不到时按通用主题处理。第三步是优先调用大语言模型出题，把学段规则、主题和输出格式要求组装成提示词发送给模型。第四步是结果校验与补足，对模型返回的题目逐题检查字段完整性、选项数量与重复情况、答案下标范围、题干长度和内容安全性，丢弃不合格的题目；若剩余数量少于要求的题目数，则从内置题库中按学段和主题抽取题目补齐。

模块的输出是一组结构统一的题目数据，以及本局题目的来源标识，用于在复盘报告中如实标注题目是模型生成还是取自题库。

设计上需要处理的关键问题是模型输出的不确定性。模块并不假设模型一定返回合规内容，而是把校验和补足作为必备环节，使模块在任何情况下都能返回数量正确的题目。

### 4.2.2 答题与判题模块设计

答题与判题模块负责接收学生的作答并给出判定结果。

学生提交单题答案时，模块比对答案下标，返回是否正确、正确答案、知识点和讲解内容，同时更新本局的答题进度和连续答对次数。判定为正确时累计正确题数，并在连续答对达到一定次数时返回鼓励提示。

一局结束时，模块接收完整的答题记录，写入答题记录表，计算正确率，结算经验值并更新用户的累计经验值。经验值的计算规则是每答对一题计2点，完成一局额外计10点。

设计上需要处理两个问题。一是重复提交。学生在网络不佳时可能重复提交同一题，模块以题目序号为标识更新而非追加记录，避免同一题被重复计数。二是倒计时的处理。倒计时由前端展示，到点时只是提示学生选择答案，不向服务端发送任何判负信息，因此不会出现因超时被扣分的情况。

### 4.2.3 复盘报告模块设计

复盘报告模块负责在一局结束后生成学习总结，内容包括正确率、掌握情况描述、薄弱知识点列表、逐题回顾和后续建议。

模块的处理分两条路径。当大语言模型可用时，把本局的答题情况整理为结构化输入，要求模型生成一段针对性的总结与建议。当模型不可用或调用失败时，改用规则模板生成：根据正确率划分档次，从答错的题目中提取知识点并按出现次数排序，据此生成对应的评价与建议。无论走哪条路径，返回结果中都带有生成方式的标识，前端在页面上如实显示。

设计上需要注意的是两条路径的输出结构必须一致，这样前端不需要为两种来源写不同的展示逻辑。模板生成的文本在具体程度上不如模型生成，但由于依据的是本局真实的答题数据，薄弱知识点的判断仍然准确。

### 4.2.4 错题本模块设计

错题本模块负责错题的收录、维护与再利用，是本系统与现有产品差别较大的部分。

收录规则为：学生答错某题时，以题干作为标识在错题本中查找，若已存在则错误次数加一并更新最近答错时间，若不存在则新增记录，同时保存选项、正确答案、学生的错误答案、解析和知识点。以题干而非题目编号作为标识的原因是，模型生成的题目每次都不一样，没有稳定的编号，而题干可以反映题目内容。

移出规则为：学生在正常答题或错题练习中答对某题时，系统从错题本中删除对应记录，视为已掌握。这一规则使错题本中的内容始终是尚未掌握的部分，不会随着练习次数增加而无限膨胀。

维护功能包括查看错题及其解析、修改题目内容、删除单条记录、清空全部记录。

复习功能为“只练错题”：按错误次数从高到低抽取若干题目组成练习卷，错误次数相同的按最近答错时间排序。这一功能不调用大语言模型，直接使用错题本中保存的题目内容，因此完全不受模型可用性的影响。

模块还需要与同伴对战协作：对战中答错的题目同样写入错题本，保证错题来源在各个入口下保持一致。

### 4.2.5 知识库模块设计

知识库模块负责管理学生上传的学习资料，并支持依据资料出题。

资料入库流程为：接收上传的文件或粘贴的文字，检查文件格式与大小，提取纯文本内容，按段落切分为若干片段，保存资料元信息与片段内容。支持txt、md、csv三种纯文本格式，安装了额外依赖时支持pdf和docx。

检索出题流程为：学生选择某份资料后进入出题环节，系统在该资料的片段中检索与主题相关的内容，取相关度较高的若干片段作为依据，连同出题要求一起交给模型。若模型不可用，则提示学生该资料需要模型支持才能出题，并允许其改用内置题库出题。

检索方式采用关键词匹配。对中文文本先做分词，统计主题词在片段中的出现次数，并结合片段长度做加权，按得分排序取前若干片段。选择这种方式的原因在2.4.2节已说明：不引入向量检索可以避免额外的模型调用与存储依赖，在没有网络的环境中仍能工作。

### 4.2.6 用户与个人中心模块设计

用户模块负责账号相关功能。注册时校验登录名的格式与唯一性、口令的长度，口令经加盐哈希后存储。登录时比对哈希结果并签发令牌。系统同时支持微信登录，通过授权码换取用户标识并在首次登录时创建账号。

游客功能用于降低首次使用的门槛。学生可以免注册进入练习，其答题记录、错题和经验值先记在一个临时身份下。学生在体验后注册账号时，系统把临时身份下的数据迁移到新账号，包括经验值、答题记录、错题和闯关记录；迁移过程中需要避免重复迁移，因此以临时身份标识为条件做一次性更新。

个人中心展示累计经验值、当前等级、段位名称、到下一级的经验差距、薄弱知识点、历史闯关记录和音效开关。等级与段位的换算规则是每50点经验提升一级，段位按等级区间划分，共八级。

### 4.2.7 扩展功能模块设计

除上述六个基础模块外，系统还设计了三项扩展功能。

基础课程题库。在原有六个科普主题之外，增加语文、数学、英语三个主题，与科普主题并列展示但分组区分，使学生既能练习科普知识，也能练习基础课程内容。题库的组织方式与科普主题一致，同样按学段分级。

同伴对战。学生选择学段与主题后发起匹配，系统为双方准备同一份试卷，比较双方的答对题数并结算经验值。设计的难点在于试卷的一致性与对手数据的真实性：试卷根据学段、主题和题目数量生成一个确定性的标识，只有标识相同的记录才被视为同一份试卷，避免拿甲卷的答案与乙卷比较；对手优先从其他学生在该份试卷上的历史作答中抽取，抽取不到时才按学生的段位生成一个正确率相当的对象兜底，并且在界面与数据中都标明对手的来源，不会把兜底对象标注为真实同学。

段位成长阶梯。按等级区间划分八个段位，从起步段位到最高段位，页面上以阶梯形式展示全部段位，标出学生当前所在的段位、与下一级的经验差距以及与最高段位的差距。达到最高段位后等级继续提升，段位停留在最高档，避免出现无法继续成长的情况。

# 第5章 功能实现与测试

## 5.1 开发环境与工具

### 5.1.1 开发环境搭建

系统的开发环境如下。

操作系统为Windows 11。开发语言为Python，版本为3.14。后端依赖包括FastAPI、Uvicorn、Pydantic、httpx和PyJWT，均为纯Python包，通过pip安装，不需要编译工具链。数据存储使用Python标准库中的sqlite3模块，不需要额外安装数据库服务。前端的小程序部分使用微信开发者工具运行，网页端直接使用浏览器，不需要构建工具。接口调试使用FastAPI自动生成的交互式文档页面。测试脚本使用Playwright驱动真实Chrome浏览器，用于端到端验证与界面审计。

开发环境的搭建过程比较简单，主要工作是安装Python依赖和确认浏览器可用。为便于重复部署，项目中提供了批处理脚本用于一键启动服务、一键生成对外访问地址和一键打包交付物。

### 5.1.2 主要开发工具

代码编辑器使用Visual Studio Code，配合Python扩展获得语法检查与调试支持。接口测试主要借助FastAPI自带的文档页面完成，对于需要反复执行的检查则写成独立脚本，避免每次手工操作。

版本管理使用Git。这里遇到的一个实际问题是：开发环境的网络无法直接与代码托管平台建立Git协议连接，因此推送改用平台的接口完成，并额外编写了一个比对脚本，通过逐文件比对内容哈希确认本地提交与远端内容一致。这个看似多余的工作并非没有价值——在开发过程中确实出现过本地已提交而远端未更新、以及远端文件与本地不一致的情况，逐文件比对能够准确指出差异所在，而不是笼统地提示需要重新推送。

浏览器自动化使用Playwright。它的作用是让测试脚本能够真正打开页面、点击按钮并读取元素的尺寸与颜色，从而验证界面行为而不仅仅是接口返回。界面审计脚本正是基于这一能力实现的。

## 5.2 功能模块实现

### 5.2.1 出题模块实现

出题模块的实现入口是一个接收主题、题目数量和学段参数的函数。函数首先对学段做归一化处理，读取该学段的参数规则，并对题目数量做区间限制，防止传入的数量超出学段允许的范围。

当配置了大语言模型密钥时，模块按模板组装提示词调用模型，提示词中包含主题、题目数量和该学段的约束条款（包括题干长度上限和选项长度要求）。模型返回的文本先经过JSON提取，再逐题补充序号、题型和知识点等默认字段。随后进行两层过滤：第一层检查内容安全性，命中不适合未成年人的词汇的题目被丢弃；第二层检查题干长度，超过该学段上限一定倍数的题目被视为超纲并丢弃。这一容差的存在是因为模型偶尔会把题干写得略长，只要不影响阅读就不必丢弃。

过滤之后，如果剩余题目数量少于要求，模块从内置题库中按主题抽取题目补齐，抽取时会排除题干已经出现的题目，避免一局之内出现重复。模块最后返回题目列表和一个来源标识，标识的取值为模型或题库，供前端在复盘页面如实展示。

当未配置密钥或模型调用失败时，模块直接跳过后半段，全部从内置题库抽题。这条路径保证了系统开箱即用。出题的处理流程如图5-1所示。

内置题库的抽题函数支持传入随机种子。当传入种子时，抽题结果由种子决定，同一组参数得到同一套题目；不传入种子时按随机顺序抽取。这一设计是为同伴对战服务的：对战双方需要通过相同的学段、主题和题目数量得到同一个试卷标识，从而确认做的是同一份卷子。

### 5.2.2 答题与判题模块实现

判题在服务端完成。学生提交单题作答时，模块根据题目在会话中的位置取出题目内容，比对答案下标，返回判定结果，同时更新本局的答题明细。

一局结束时，模块接收完整的作答明细，计算答对题数与正确率，按每答对一题2点、完成一局额外10点的规则结算经验值，并把用户表中的累计经验值加上本次所得。答题记录、经验值和错题数据在同一个流程中写入，保证三者一致。

答题明细以JSON格式整段存入数据库而不是逐题建行。这样做是因为明细只在复盘时整段读取，不会按单题查询，逐题建行会带来不必要的行数增长。重复提交同一题时，模块按题目位置更新已有记录而不是追加，避免同一题被重复计入。

### 5.2.3 复盘报告模块实现

复盘报告的生成有两条路径，由同一个函数按模型可用性选择。

模型可用时，模块把本局的主题、学段、正确率和逐题结果整理成结构化的输入，要求模型输出包含总体评价、薄弱知识点和建议的报告文本。模型不可用时，模块改用规则模板：按正确率划分为几个档次，从答错的题目中提取知识点并按出现次数排序，套用对应的评价用语生成报告。

两条路径的返回结构完全一致，都包含评价文本、薄弱知识点列表和生成方式标识。前端不需要区分来源，只在页面角落注明报告由模型生成还是由模板生成。这样处理的原因在2.4.1节已经说明：不假设模型一定可用，但也不因为模型不可用就降低功能的完整度。

### 5.2.4 错题本模块实现

错题本模块围绕“答错入库、答对移出”这一对规则实现。

入库时以题干为标识查找已有记录。若存在，则错误次数加一并更新最近答错时间；若不存在，则新增一条记录，同时保存选项、正确答案、学生的错误答案、解析和知识点。选择以题干而非题目编号作为标识，是因为模型每次生成的题目内容不同，没有稳定的编号可用，而题干能够反映题目内容。

移出时按题干删除对应记录。这一动作在正常答题和错题练习两条路径上都会触发，因此学生只要答对，错题本中就不会再保留这道题。

维护功能包括按错误次数排序的列表查询、单条记录的修改、单条删除和整体清空。“只练错题”功能按错误次数从高到低取题组卷，错误次数相同的按最近答错时间排序，取题数量按当前学段的规则确定。这一功能直接读取错题本中保存的题目内容，不调用大语言模型，也不访问题库，因此完全不受外部服务可用性的影响。错题本为空时，接口返回明确的提示而不是空列表，前端据此引导学生先做一轮练习。

同伴对战结算时，答错的题目也走同一个入库函数，因此对战中产生的错题同样会进入错题本，避免了不同入口下错题状态不一致的问题。

### 5.2.5 知识库模块实现

知识库模块的实现在数据入库和检索出题两个环节。

数据入库环节，模块接收上传的文件或粘贴的文字。对于文件，先检查扩展名是否在允许范围内、大小是否超过限制，再按类型提取纯文本：纯文本格式直接读取，PDF格式借助pypdf提取，Word格式借助docx2txt提取。提取出的文本按段落边界切分为若干片段，与资料元信息一起写入数据库。切分时保留段落边界而不是按固定字数硬切，是为了让片段保持语义完整，检索出来的内容才便于模型理解。

检索出题环节，模块接收资料标识和主题，在属于该资料的片段中检索相关内容。检索采用关键词匹配：先对主题和片段分别做分词，统计主题词在片段中的出现次数，再结合片段长度做加权，按得分排序取前若干片段。取出的片段作为依据拼入提示词，要求模型只依据这些片段出题。若模型不可用，接口返回提示，引导学生改用内置题库。

这里没有采用向量检索，原因在于向量检索需要额外的模型调用与向量存储，在没有网络的环境中无法工作，而讲义类资料篇幅有限、术语集中，关键词匹配已经能够满足需要。

### 5.2.6 用户与个人中心模块实现

账号部分的实现包括注册、登录、微信登录和游客体验四条路径。

注册时校验登录名的格式与唯一性、口令的长度，用随机生成的盐值对口令做哈希后存储。登录时取出该账号的盐值，用相同算法计算哈希并与存储值比对，比对通过后签发令牌。令牌的载荷中包含用户标识和签发时间，密钥从配置读取。

游客体验的实现方式是创建一个标记为游客的账号并签发令牌。学生在体验后注册时，模块把游客账号下的经验值、答题记录、错题和闯关记录一并迁移到新账号，并以游客标识为条件做一次性更新，防止重复迁移造成数据翻倍。

个人中心的数据由等级与段位模块统一计算。该模块以50点经验为一级，提供等级换算、段位查找、到下一级的进度和到下一段位的进度四个结果，其中到下一段位的进度需要从该段位的起始等级重新计算，否则会把上一段位积累的经验算进本段位，进度条会出现虚高。

### 5.2.7 扩展功能实现

基础课程题库的实现方式与科普题库一致，差别只在主题分组。题库载入模块在提供主题列表时按类别分组，把语文、数学、英语归入基础课程，把天文、地理、生物、物理、化学、科技归入科普主题，前端据此分组展示。语文与英语题目以人工核对的方式维护，数学题目由程序生成：数字随机取值，正确答案由程序计算得出，干扰项取计算结果的邻近值并断言彼此不同。这样处理是因为手写大量算术题难免出现算错的情况，而由程序计算并校验可以从源头避免。

同伴对战的实现分为匹配与结算两步。匹配时，模块先根据学段、主题和题目数量生成试卷标识，再从已结算的对战记录中查找同一份试卷、同一学段、同一主题的其他学生记录，从中随机取一条，把该学生本人的作答明细作为对手数据；如果查不到符合条件的记录，则按学生的等级生成一个正确率相当的对象，其作答由模拟产生。对手数据的来源在记录中以类型字段区分，界面上的对手名称也据此显示，不会把模拟对象标注成真实同学。结算时，模块重新计算双方的答对题数，判定胜负，按规则结算经验值，答错的题目写入错题本。

这里需要说明一处实现上的修正。对战功能完成初步实现后，检查脚本发现界面标注的“对手是另一位同学的成绩”与实际取用的数据不符：代码取的是对方那一局的对手作答，而不是对方的作答。这一问题的成因是记录中存在两列容易混淆的作答数据。修正后改为取本人作答列，并增加了试卷标识相同的约束，使比分比较有了明确的前提。

段位阶梯的实现集中在等级与段位模块中。模块以常量定义每个段位的名称、等级区间和经验起点，对外提供段位列表和当前进度两个查询结果。段位列表供前端绘制阶梯，当前进度供前端标出学生所处的位置。等级与段位的换算只在这一处定义，避免了前后端各写一套规则导致显示不一致。前端在接口不可用时使用内置的同一份段位数据作为兜底，保证页面不会空白。

## 5.4 系统测试方案设计

# 第6章 结 论

## 6.1 研究工作总结

本课题围绕中小学生科普知识闯关系统的设计与实现开展了工作，完成的主要工作可以归纳为四个方面。

第一，明确了系统的功能定位与需求依据。通过文献梳理发现，现有的教育类与科普类应用普遍存在三个问题：题目依靠固定规则生成导致重复、错题只记录不诊断、难度无法随学生水平调整。通过问卷调查进一步验证了这三点：在使用过同类应用的填写者中，选择“题目重复”“答错只有对错没有讲解”“难度不适合孩子水平”的比例分别为69.1%、57.4%和48.5%，排在各问题项的前三位。同时，调查显示超过半数的填写者对游戏化机制存在分散注意力的顾虑，这成为系统在激励机制设计上保持克制的主要依据。

第二，完成了系统的设计与实现。系统采用前后端分离的分层架构，实现了出题、答题与判题、复盘报告、错题本、知识库、用户与个人中心六个基础功能模块，并设计了语文、数学、英语基础课程题库、同伴对战与段位成长阶梯三项扩展功能。系统包含24个学生端接口和14个管理端接口，数据库设计11张数据表，内置题库225道题，覆盖9个主题并按三个学段分级存放。前端提供小程序端、网页端学生端和管理端三个入口。

第三，解决了实现过程中的几个具体技术问题。针对大语言模型输出结构不稳定的问题，设计了调用约束、接收校验和题库补足三个环节的处理流程，并为出题、复盘报告和错题练习三条链路分别设计了降级方案，使系统在不配置模型密钥或没有网络的情况下仍能完成完整的练习流程。针对学段适配，把题量、题干长度上限和选项长度上限落实为可检查的参数，并保证低年级与初中不共用题干。针对错题的多路径一致性，以题干为标识实现答错入库并累计、答对移出，使对战中产生的错题同样进入错题本。针对同伴对战的公平性，通过试卷标识确认双方所做题目一致，并优先取真实学生的历史作答作为对手数据。

第四，建立了可重复执行的验证手段。为各个模块编写了检查脚本，并整合为一条命令可执行的整体验收流程，共17项检查，覆盖接口功能、题库规范、学段分离、错题本增删改查、账号与错题收录、管理端数据分类、段位换算、对战流程以及界面渲染与对比度。在开发过程中，这套检查手段发现了若干仅靠浏览代码或手工点击难以察觉的问题，包括错题收录的调用时机错误、对战对手数据取错列、题库中答案与解析不一致、窄屏下的横向溢出与多处文字对比度不足。这些问题的修正过程构成了本课题在工程实践上的主要收获。

## 6.2 研究存在的不足

系统虽然达到了预定的设计目标，但仍存在以下不足。

第一，缺少真实的教学效果验证。本课题的测试集中在系统功能、性能和界面层面，验证的是系统是否按设计工作，而没有验证使用系统是否真正提高了学生的科普知识水平。要做到这一点，需要选取对照班级开展持续数周的教学实验，比较使用前后或与不使用系统的对照组之间的差异。受时间与条件限制，本课题没有开展这一工作，因此系统在“用起来效果如何”这一层面还缺少数据支撑。

第二，问卷调查的样本有限且集中在特定范围。有效问卷138份，填写者为家长和小学教师，样本量偏小，且填写者对孩子学习情况的判断属于间接观察，可能与学生的真实感受存在偏差。问卷中关于学生使用感受的部分没有直接从学生本人收集，这一点在结论的推广上需要谨慎。

第三，出题质量依赖外部模型。虽然系统通过校验和过滤把住了结构和内容安全的底线，但题目的知识准确性和表述质量仍取决于所用模型的能力。题库兜底可以保证题量，但内置题库的题目数量有限，长期使用仍会出现重复。

第四，知识库的检索精度有限。系统采用关键词匹配而非向量检索，对术语集中的讲义资料效果尚可，但对于表述方式与主题词差异较大的资料，检索效果会下降。这一取舍是用效果换取离线可用性，在具备网络条件时并非最优选择。

第五，题库的覆盖面还不完整。当前题库共225道题，平均每个主题25道，按学段分下来每个学段在每个主题上只有8至9道题，学生连续练习几次就会遇到重复。要让系统在长期使用中保持新鲜度，需要持续扩充题库。

第六，学段适配的参数依据不够充分。各学段的题干长度上限和选项长度上限是参考课程标准与教学经验设定的，没有经过阅读能力测试的验证，属于经验性参数。

## 6.3 后续工作展望

针对上述不足，后续工作可以从以下几个方向展开。

在教学效果验证方面，可以与学校合作开展小规模的对照实验，选取两个平行班，一个班在课外使用系统进行科普练习，另一个班维持原有方式，经过一段时间的教学后比较两班在科普知识测试中的表现，并收集学生和教师的使用反馈，用数据检验系统的实际作用。

在题库建设方面，可以扩充内置题库的题目数量，使每个学段在每个主题上的题目数达到能够支撑多次练习的规模；同时可以对题库的难度做更细的标注，使抽题时能够依据学生的历史正确率调整题目难度，实现更细致的自适应。

在检索方式方面，可以在保留关键词检索作为离线兜底的前提下，增加向量检索作为可选方式：在具备网络条件时使用向量检索提高精度，在无网络时回退到关键词检索。这样可以同时兼顾效果与可用性。

在功能扩展方面，可以考虑增加面向教师的内容管理能力，例如由教师布置指定主题的练习任务并查看班级整体的完成情况；也可以考虑增加学习提醒与阶段性总结，帮助学生形成固定的练习习惯。

在参数验证方面，可以通过小范围的阅读能力测试或与语文教师的研讨，对题干长度与选项长度的上限做更可靠的校准，使学段适配的依据从经验判断转向可验证的依据。

## 一、出题与降级

出题函数按“模型优先、题库兜底”的顺序实现，并对模型返回内容做两层过滤后补足题量。来源标识用于前端如实展示题目出处。

```python
def generate_questions(topic: str, count=None, grade=None):
    """出题：优先 DeepSeek；失败 / 无 Key / 内容不合规 时降级题库。"""
    g = grades.normalize_grade(grade)
    rule = grades.grade_rule(g)
    count = grades.clamp_count(count, g)

    if settings.deepseek_api_key:
        try:
            raw = _call_llm(QUIZ_PROMPT.format(
                topic=topic, count=count, grade_clause=grades.prompt_clause(g)))
            data = _extract_json(raw)
            cleaned = []
            for i, q in enumerate(data.get("questions") or []):
                if not isinstance(q, dict):
                    continue
                q["id"] = i + 1
                q.setdefault("type", "single")
                q.setdefault("knowledge_point", "科普知识")
                cleaned.append(q)

            # 第一层过滤：内容安全
            cleaned, dropped_unsafe = safety.filter_questions(cleaned)
            # 第二层过滤：题干长度（远超该学段承受范围视为超纲）
            limit = int(rule["stem_max"] * STEM_TOLERANCE)
            cleaned = [q for q in cleaned if len(str(q.get("stem", ""))) <= limit]
            cleaned = cleaned[:count]

            if cleaned:
                # 被过滤掉的题目用题库补齐，保证题量与体验
                if len(cleaned) < count:
                    extra = _bank_questions(
                        topic, count - len(cleaned),
                        exclude_stems=[q.get("stem") for q in cleaned], grade=g)
                    cleaned.extend(extra)
                return {"title": data.get("title") or topic,
                        "questions": cleaned, "source": "ai"}
        except Exception:
            pass  # 落到下面的题库分支

    # 降级：内置题库按主题与学段抽题
    return {"title": topic, "questions": _bank_questions(topic, count, grade=g),
            "source": "bank"}
```

## 二、判题与经验值结算

结算函数在一次调用中完成逐题比对、明细记录、经验值结算和错题本维护，保证四者在同一流程中保持一致。

```python
def submit_answer(quiz_id, answers, user_id=None, duration_ms=0):
    """判题与结算：逐题比对 → 记录明细 → 结算经验值 → 维护错题本。"""
    row = db.query_one("SELECT * FROM quiz_sessions WHERE quiz_id=?", (quiz_id,))
    if not row:
        return None
    questions = db.loads(row["questions_json"]) or []
    total = len(questions)
    correct = 0
    details = []
    for i, q in enumerate(questions):
        user_ans = answers[i] if i < len(answers) else -1
        right = int(q.get("answer", 0))
        is_correct = (user_ans == right)
        if is_correct:
            correct += 1
        details.append({
            "id": q.get("id", i + 1),
            "stem": q.get("stem", ""),
            "options": q.get("options", []),
            "user_answer": user_ans,
            "correct_answer": right,
            "is_correct": is_correct,
            "analysis": q.get("analysis", ""),
            "knowledge_point": q.get("knowledge_point", ""),
        })
    accuracy = round(correct / total * 100, 1) if total else 0
    db.execute(
        "INSERT OR REPLACE INTO answer_records(quiz_id, user_id, records_json, "
        "total_questions, correct_count, accuracy, duration_ms) VALUES(?,?,?,?,?,?,?)",
        (quiz_id, user_id, db.dumps(details), total, correct, accuracy,
         int(duration_ms or 0)))

    # 经验值结算：完成闯关 +10，每答对一题 +2
    xp = XP_FINISH + correct * XP_PER_CORRECT
    if user_id:
        db.execute("UPDATE users SET total_xp=total_xp+?, "
                   "updated_at=datetime('now','localtime') WHERE id=?", (xp, user_id))

    # 错题本维护：答错入库并累加次数；答对视为已掌握，从错题本移除
    added = wrongbook.record_wrong(user_id, quiz_id, details)
    mastered = wrongbook.mark_mastered(user_id, details)

    return {"quiz_id": quiz_id, "total": total, "correct": correct,
            "accuracy": accuracy, "xp_gained": xp,
            "wrong_added": added, "mastered": mastered}
```

## 三、同伴对战的真人对手选取

选取对手时必须同时满足“取本人作答”和“同一份试卷”两个条件，否则比分比较没有意义。

```python
def _real_ghost(grade, theme, exclude_user_id, paper_key, total):
    """从已结算的 PK 局里找一位真实对手，把**他本人的作答**拿来当对手。

    1. **要取他本人的作答**（`my_answers_json`），不是他那局的对手的作答；
    2. **必须是同一份卷子**（`paper_key` 相同、题量相同）。
    """
    rows = db.query(
        "SELECT p.match_id, p.user_id, p.my_answers_json, p.my_correct, p.total, "
        "u.nickname FROM pk_matches p LEFT JOIN users u ON u.id = p.user_id "
        "WHERE p.status=1 AND p.grade=? AND p.theme=? AND p.user_id IS NOT NULL "
        "AND p.user_id != ? AND p.paper_key=? AND p.total=? "
        "AND p.my_answers_json != '[]' "
        "ORDER BY p.id DESC LIMIT 40",
        (grade, theme, exclude_user_id or -1, paper_key, total))
    if not rows:
        return None
    row = random.choice(rows)
    try:
        answers = json.loads(row["my_answers_json"])
    except Exception:
        return None
    if not isinstance(answers, list) or len(answers) != total:
        return None
    return {"kind": "user", "user_id": row["user_id"],
            "name": row["nickname"] or "一位同学",
            "answers": answers, "source_quiz": row["match_id"]}
```

## 四、段位进度计算

等级与段位的换算集中在一处实现。计算到下一段位的进度时需要从该段位的起始等级重新算起，否则会把上一段位积累的经验计入本段位。

```python
XP_PER_LEVEL = 50

def progress(total_xp):
    """完整的成长进度：当前等级、段位、到下一级的进度、到下一段位的进度。"""
    xp = max(0, int(total_xp or 0))
    level = level_of(xp)
    rank = rank_of_level(level)
    nxt = next_rank(level)

    in_level = xp % XP_PER_LEVEL
    level_progress = {
        "level": level,
        "xp_in_level": in_level,
        "xp_per_level": XP_PER_LEVEL,
        "xp_to_next_level": XP_PER_LEVEL - in_level,
        "percent": int(round(in_level * 100.0 / XP_PER_LEVEL)),
    }
    return {"level": level, "rank": rank, "level_progress": level_progress,
            "next_rank": nxt, "rank_progress": rank_progress}
```
